# MIR Optimization Daily Summary (2026-04-10 ~ 2026-04-14)

## Overview

Extended debugging session focused on two classes of MIR execution divergence: **self-looping block PHI corruption** (contract 0x205d) and **parse-time fixpoint propagation failure** (contract 0xD5eC). Both stem from runtime rebuild paths that destroy loop-carried values or fail to propagate PHI changes to downstream blocks.

---

## Phase 1: Self-Loop PHI "missing result for def MirADD" (Block 22413801, Contract 0x205d)

### Problem
Block@1052 is a self-looping block (children=1082,1052). Its PHI at instruction #8 references MirADD at instruction #15 — a "future def" within the same block. On the second iteration, `evalPhi` falls back to the snapshot path and returns zero instead of the previous iteration's computed value.

### Root Cause Chain
Multiple independent runtime paths triggered `connectEdge` → `invalidateBlockResults` → cleared non-PHI results → PHI fell back to zero:

1. **evalPhi snapshot guard too narrow** (`2943478ef`): Only checked `MirPHI` ops for same-block def fallback, missed `MirADD` and other non-PHI defs in self-looping blocks.

2. **Parse-time entry stack rebuild on back-edge parents** (`2e878335f`): `tagIncomingEpoch` set runtime epoch on self-loop edge → line 921 rebuild trigger fired for back-edge parents.

3. **needsRuntimeEpoch snapshot refresh** (`70da2b936`, `cd33f87c8`): Forward-edge entry to loop headers triggered the `needsRuntimeEpoch` path → `connectEdge` → rebuild.

4. **refreshEdgeIfNeeded** (`cd6aab3e7`): `runtimeBecameDynamic` caused snapshot recomputation on self-loop edge → `connectEdge` → `built=false`.

5. **Loop-exit edge materialization** (`afc1cedbe`): SLOAD results from loop body were materialized into constants on loop-exit edges → cached CFG served stale values to future calls.

6. **connectEdge runtime back-edge invalidation** (`37f234b3b`): The definitive fix — `connectEdge` itself was calling `SetEntryStack(nil)` + `built=false` on the self-loop edge at runtime, directly causing rebuild → `invalidateBlockResults` on every loop iteration.

### Fix Summary
- `connectEdge`: At runtime (`runtimeEpoch != 0`), skip invalidation when the edge targets a genuine loop header (`blockInLoop(child)`)
- `blockInLoop`: Precisely detect self-loops and tight 2-node cycles (not PC-based heuristics)
- `evalPhi`: Generalize same-block def guard from `MirPHI` to any `defBlockNum == cur.blockNum`
- Multiple runtime paths: Skip snapshot refresh / rebuild for loop headers and back-edge entries

## Phase 2: Parse-Time Fixpoint Propagation (Block 22413801, Contract 0xD5eC)

### Problem
Contract `0xD5eC82071D0c870BfBa60B58A0AA52E42A3BEFba` crashed with `"invalid jumpdest 0x0"`. PHI operands in block@2148 referenced block@562's PHI defs (never executed on the actual path), causing zero-value jumpdest.

### Root Cause Chain

1. **connectEdge guard too broad** (`4e5f189ab`): The initial `parent.firstPC >= child.firstPC` guard blocked **all** high-to-low PC edges, including legitimate forward edges (utility function returns). Block@2507→block@2148 was incorrectly treated as a loop back-edge.

2. **blockInLoop false positives** (`c86efcbf7`): `blockInLoop` used `child.firstPC <= block.firstPC` which matched shared merge points (block@2148→block@746). Replaced with precise self-loop / tight-cycle detection.

3. **Runtime snapshot refresh on pending-rebuild blocks** (`94fec262c`): Blocks marked `built=false` from parse-time had symbolic `incomingStacks` that correctly differentiated paths. Runtime snapshot refresh materialized values → different symbolic paths looked identical → no PHIs created → stale def references leaked through.

### Fix Summary
- `connectEdge` guard: Narrow to `blockInLoop(child)` — only genuine loop headers skip invalidation
- `blockInLoop`: Detect self-loops (`child == self`) and tight 2-node cycles, not PC-based heuristics
- `needsRuntimeEpoch` path: Skip blocks with `built=false` (pending parse-time rebuild) to preserve symbolic incoming stacks

## Key Design Insights

### Why Only Self-Loops Need Protection
The fundamental issue is PHI operands referencing **future defs within the same block**. This only happens in self-looping blocks where instruction #N's PHI references instruction #M>N. In multi-block loops (A→B→A), PHI operands reference defs in other blocks, and cross-block references are stable via `defKeyToResIdx`.

### PC-Based Heuristics Are Unreliable for EVM
EVM bytecode layout puts utility functions (internal `_add`, `_sub`, error handlers) at high PCs. These jump back to low-PC merge points without forming loops. `parent.firstPC >= child.firstPC` produces massive false positives. Genuine loop detection requires structural analysis (self-loops, parent-child cycles).

### Runtime vs Parse-Time Rebuild Semantics
- **Parse-time rebuilds** are essential for PHI creation (fixpoint convergence)
- **Runtime rebuilds** on loop headers are destructive: they create new MIR objects with potentially new resIdx, invalidating back-edge PHI operands
- **Pending-rebuild blocks** (`built=false`) should not have their symbolic incoming stacks replaced with materialized runtime values — doing so eliminates necessary PHIs
